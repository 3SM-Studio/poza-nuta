# Participant identity and nickname consistency

Implemented locally on 2026-10-17 as part of [Enterprise integration](enterprise-integration.md). No production or existing development database changes.

The authoritative identity is the canonical **event participant ID**. A nickname is an editable event-scoped label. Queue, current-performance and history cards, participant details and the public queue now read that current label. `song_requests.display_name` and `singer_name` remain original request snapshots. `requestDisplayName` is labelled “Zgłoszono jako”, never presented as proof of the immediately preceding nickname. Legacy requests without membership retain their own original label and have no guessed participant identity/count.

`src/server/queue-presentation.ts` provides a shared, event-scoped batched read model. Known aliases combine history by canonical membership, including rename events from retired profiles. Participants without requests still have their real rename history. Operator metadata includes current/original label, canonical ID, confirmed event-wide completion count, current-performance flag, join date, real rename events, merged-profile indication and recorded insertion explanation. The public queue receives only its existing fields with the current singer label; private audit history and statistics are not added to the public API.

Migration 0033 records only future actual changes of `display_name`, with private before/after/time. A no-op update produces no rename. The trigger function has an empty search path, restricted execution, transactional audit/revision/broadcast and no participant information in broadcast payloads. Existing participants, names, request snapshots and earlier audits are not rewritten. A name change advances the stream snapshot revision, not `intent_version`. The client gesture fingerprint ignores presentation fields. Pending intents replay over refreshed names; naming changes do not cancel structurally valid DnD.

Rename retains the existing participation-only lifecycle/credential lock order. An intermediate integration incorrectly added the session queue mutex and caused the contention tests to fail. That change was removed rather than weakening those tests. Renaming remains possible when song submission is disabled, subject to existing session rules. Merge continues to use its original consent, canonical membership, event mutex and credential protection. It changes ownership/fairness and can invalidate a Fair Sort preview; it is not merely a rename.

“First performance” means **zero confirmed completed performances**, independently of join date. Starting alone is not a completion. A separately confirmed cancellation of `now` returns it to pending and records cancellation without incrementing count. Explicit finish and the pre-existing start-next finishing action append completion facts. Restoring a completed request preserves its confirmation; another actual performance can add another confirmation. Existing explicit `event_queue_done` audits and restores explicitly observing a `done` source are included, even after a historical restore. New confirmation/action pairs deduplicate by request version. The same shared projection drives operator counts and v2. Legacy current `done` counts once if its completion is otherwise unrecorded. Before restoring such a legacy row, preserve the observed fact with labelled provenance; an unknown date stays unknown for waiting-credit calculations. `hasPerformed` keeps its old status-based API semantics for compatibility. See the [fairness ADR](../architecture/adr-fair-queue-v2.md) for the precise distinction.

The UI adds discreet first/count labels, an existing participant-history link, original request label, expandable actual rename history and merged-profile notice. It preserves current layout, confirmations, responsive DnD and PL/EN/UK catalogs. Participant history explains that restoring a request does not erase confirmed performances. No new identity system, global nick matching, authentication token storage or business-table browser access was introduced.

Verification is recorded in the integration ledger, including PostgreSQL rename rollback and browser-role denial, no-op/real rename after a populated 0032→0033 upgrade, no invented history, unchanged stored snapshots/semantic versions, known-merge history aggregation, cancel/finish/restore, two live operator accounts and a mobile-sized participant context. Component tests cover rename during a pending independent mutation/gesture and first-performance labels when legacy `hasPerformed` is true. Physical devices, Safari and native assistive technology have not been certified.

Migration review: additive, moderate operational risk because a failed audit or Realtime send rolls back the participant update. No backfill or NOT NULL/FK changes. Future authorised verification should check migration hashes; trigger existence and grants; a no-op rename; an actual rename reaching both operators; preserved request snapshots/semantic versions; event-scoped audits and minimal private messages. Roll back application/engine without deleting history; handle a defective trigger with a separately reviewed forward fix, not destructive database rollback.

Unrecoverable historical gaps remain explicit: a physically performed song with no surviving completed state or supporting audit cannot be reconstructed. An unknown completion date contributes a confirmed count where a source-state audit proves it, but contributes no fabricated foreign-turn timestamp. The actual audit observation conservatively anchors subsequent waiting. This does not manufacture nickname aliases or rewrite old rows.
