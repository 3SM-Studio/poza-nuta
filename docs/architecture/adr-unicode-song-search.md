# ADR: Unicode song-search projection

Date: 2026-10-16. Status: implemented for explicit local validation; production activation requires separate approval.

The existing ASCII search keys delete non-Latin scripts and all combining marks. Replacing query normalization cannot repair those persisted keys. Keep the existing rendition identities, original strings, legacy keys, provider upserts and session contracts intact.

Add private `song_search_documents` and provenance-bearing `song_search_aliases`. Migration 0031 installs one deterministic SQL projection writer for every source insert/update, including existing iSing/KaraFun writers. Backfill missing documents in short transactions with source-row locks and `SKIP LOCKED`. No source song is rewritten. Both new tables use RLS without browser policies, and public roles cannot invoke helper functions. Trigger functions use a fixed pg_catalog search path, qualified objects, narrow trigger inputs and revoked public execution.

Normalization v2 uses Unicode 17 NFKD, full default C/F case folding, canonical decomposition and Latin-base accent folding. Keep combining marks for other scripts, joiners, letters and numbers. Strip directional formatting controls from search keys and turn punctuation/emoji into separators. Preserve original display values. The SQL generator pins scalar decompositions and character-class ranges because PostgreSQL and Node may embed different Unicode versions. Hangul decomposition is algorithmic. Activation requires the verified Unicode 17 application runtime. Never change v2 in place after release: a future algorithm gets a new version/projection migration.

Whitespace-delimited tokens (maximum 16, deduplicated) support existing Latin/Cyrillic/Greek queries. Continuous scripts use literal prefix/substring matching, not language-independent word stemming. GIN bigrams and CJK unigrams supply candidates for short and unspaced queries; the literal predicate rechecks them. Single Han/kana/Hangul queries are allowed; single Latin letters remain below the threshold. Queries containing only separated single non-CJK letters have no useful grams and use exact identity/alias matches only. This avoids empty-array containment scans. Typo fallback is restricted to Latin/Cyrillic/Greek queries with at least three non-space code points and useful grams. Other scripts use deterministic literal matching and reviewed aliases.

Rank original combined identity, exact title, exact artist, prefix, identity tokens and substring ahead of aliases and loose fuzzy matches. Five independently bounded candidate branches supply at most 1,900 rendition IDs. Results use stable tier/similarity/C-collated keys/source/id ordering and query/engine-bound cursors, 50 items per page. This retains the previous bounded-window search semantics; it is not exhaustive traversal of every broad catalog match. Ordinary catalog browse remains available for traversal.

Trusted aliases are spelling alternatives, not semantic translations. No guessed universal romaji/pinyin/romanization or automatic transliteration is enabled. Alias write APIs/UI are a later authorized feature. Browser locale never changes matching, ranking or domain values.

`SONG_SEARCH_ENGINE=legacy` remains the default. Explicit `unicode-v2` activation follows migration, complete backfill, validation and appropriate database-role grants. Roll back reads by returning to legacy; retain the additive tables/functions and all source rows. This task performs no remote activation.

Primary references: [Unicode normalization](https://www.unicode.org/reports/tr15/), [Unicode 17 case-fold data](https://www.unicode.org/Public/17.0.0/ucd/CaseFolding.txt), [PostgreSQL 17 trigram behavior and index limitations](https://www.postgresql.org/docs/17/pgtrgm.html), [Drizzle custom migrations](https://orm.drizzle.team/docs/kit-custom-migrations). Exact test evidence and deployment preflight are in `docs/features/universal-multilingual-song-search.md`.
