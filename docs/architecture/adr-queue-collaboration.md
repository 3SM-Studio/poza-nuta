# ADR: local operator intents over a versioned canonical queue

Status: implemented and verified in isolation (PostgreSQL 17 and optimized browser runtime), 2026-10-17. Production rollout is not authorised by this task.

The audit starts from release `703c145dc21a2b1eb58370a93058402ffbb4f48b`. The existing personal configuration and production-readiness handoff are pre-existing changes and are outside this task. No production service, event, domain or deployment is modified.

## Observed problems

`EventQueuePanel` already projected optimistic operations, but a single Promise chain serialized every HTTP mutation. `placementBusy`, the pending-operation check in `handlePlacement`, and `canDrag` disabled the whole board. Both Realtime and manual GET responses were deferred whenever any mutation was pending. Placement compared an exact version vector for the entire queue, rejecting unrelated edits. A request version also changes when another song merely renumbers its position. HTTP retries had no durable server receipt. A start operation completed the current performance without a client precondition identifying that performance.

## Decision

Keep App Router, Drizzle, Supabase Auth, existing RBAC, event/session mutexes, integer contiguous positions and the existing Fair Queue mathematics. Introduce `/queue/sync` alongside the legacy API. Business data still comes exclusively from the authorised server API. Broadcasts are invalidations, never queue data.

An operation contains a UUID, a per-tab/device UUID, the expected server actor, request ID, source status and semantic intent version. A placement contains before/after neighbour IDs and their semantic versions, not a global queue version. Unrelated shifts and insertions can be rebased; a moved/removed neighbour, reversed gap, changed source or explicit Fair Sort barrier returns 409. Two distinct songs inserted into the same surviving gap are ordered by serial transaction acceptance; neither is dropped. Neighbour ordering is preserved. A start also identifies the observed current performance/version. Start/start cannot silently replace the winner. The client sequences dependent intentions and start/done, while unrelated requests use up to four concurrent HTTP requests. The database still serializes each event's transactions to preserve atomic positions, capacity and Fair Queue invariants.

`intent_version` is distinct from the existing row `version`: status changes and explicit primary moves advance it; incidental renumbering does not. Legacy mutations also advance primary semantic versions. Idempotency is scoped to event and operation, bound to verified operator/device and canonical payload fingerprint. The domain action, receipt and audit correlation commit atomically. A retry returns a fresh canonical snapshot and acknowledgement, not a stale stored queue. UUID/device/actor fields grant no permission. Every write revalidates session, membership, lifecycle and existing request-capacity checks.

The client keeps a canonical base plus a bounded, durable IndexedDB outbox of at most 64 intents. It stores IDs, preconditions and operation metadata, never authentication credentials, participant tokens, names, notes or a persisted queue snapshot. Storage is scoped by verified actor, organisation, event and device. A document owns its device ID through an exclusive Web Locks lease; copied sessionStorage in a duplicated tab rotates the copied device ID before opening an outbox. Reloads reclaim the original ID after the old document releases its lease. Missing Web Locks/storage fails closed. Responsive duplicate mounts share one controller/writer. UI changes precede persistence/network; POST waits for successful local persistence. Network failures retain the same UUID for bounded automatic retry and explicit recovery. Terminal conflicts retain the intent and display canonical rows; they require an operator decision. Ambiguous commits cannot be discarded as if they were unsent. Reauthentication/account switching cannot replay another actor's operations.

Snapshots use a transactionally coherent stream revision and items. Older snapshots cannot replace newer state; receipt acknowledgements can still resolve already committed work. New canonical state is accepted while local writes are pending, then remaining intentions are replayed. A changed gesture is cancelled visibly rather than writing an obsolete numeric drop. Version-only changes that leave the visible/semantic queue unchanged must not invalidate a gesture.

The trigger coalesces row writes into one event revision and one private broadcast per event/transaction, with a transaction-local marker. Its message is visible through Realtime only after the transaction commits. This uses the existing [Supabase database broadcast mechanism](https://supabase.com/docs/guides/realtime/broadcast), not a client-side pre-commit broadcast. Payload: event ID, event type, SQL operation, timestamp and decimal revision; no business rows or personal data. Client deduplication uses the trusted API revision, not an unconditionally trusted broadcast watermark. Sequence gaps, subscribe, reconnect and focus fetch a snapshot. No queue interval polling is introduced. Public and participant topics retain their existing contracts and authorisation.

## Alternatives and limits

No CRDT or last-write-wins model is introduced for status/performance decisions. Fractional ranks would add a new ordering model without removing status conflicts; existing contiguous ordering remains. Coalescing successive moves is deferred: durable one-to-one receipts and auditability are preferable until measurements show that reducing dependent writes is needed. Independent operations already avoid head-of-line blocking.

This release is local-first interaction and durable intent recovery, not an installable offline PWA: an already open tab works offline, but a cold application navigation still needs the server. No auth/session material is stored in the outbox. Device identifiers are correlation metadata, not proof of a physical device. Physical touch, Safari and native assistive technologies require a separate actual-device check.

## Verification and migration

Additive Drizzle migration 0032 creates private `queue_streams` and `queue_operation_receipts`, a constant-default semantic-version column and restricted trigger functions. Existing data and positions are retained. Apply only to an owned disposable PG17/Supabase fixture during this task. Before a future release: verify existing migration hashes, backup/restore, browser-role denial and supported writer lock order. An application rollback keeps additive metadata/receipts; no automatic DOWN or production schema change is authorised here.

Required evidence: real PG17 races, source/anchor/start conflicts, idempotency and rollback, negative API/RBAC/CSRF tests, real two-context Realtime, delayed/lost responses, rapid DnD, durable recovery, stale snapshots and optimised-build responsiveness. Target local click-to-next-render-frame p95 ≤100 ms; cross-browser confirmed convergence p95 <2 s and maximum 5 s under healthy local networking. Injected latency is reported separately. Headless/emulated tests do not certify physical paint or tablet touch.
